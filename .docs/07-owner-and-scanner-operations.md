# Owner and door operations (Step 4)

The owner dashboard is `/admin` on the configured admin hostname; door staff use `/staff` and `/scanner.html` on the configured staff hostname. These are surfaces of the existing application. API role checks and Origin checks apply on every request. The final hosting/domain configuration remains Step 5.

## Owner work

- Payment review shows buyer, expected amount, receipt attempts, transfer reference, sender, flags and hold urgency. Check the actual credit in the bank app before approving. Refresh expired receipt links. Rejected payments can allow re-upload or close the case. Expired orders with pending proof can be revived if inventory is still available, or dismissed. Capacity failure means arrange the refund manually.
- Refunds require password re-entry and acknowledgement of already checked-in tickets. Record the refund after returning money in the bank app. Choose restocking only when appropriate. Resends go to the original purchaser; the email delivery screen shows queue/provider state.
- Save event drafts, upload a JPEG/PNG/WebP banner, add venue/organizer and tiers, then publish. Unconfirmed dates remain visible as announced later and sales stay closed. All form times use Africa/Lagos. Tier capacity cannot go below sold plus reserved. Referenced records cannot be deleted; cancel events or deactivate staff instead.
- The venue editor can search Google Places and populate address, place ID and coordinates. Missing launch configuration shows a clear fallback; verify manually entered addresses/coordinates. About/Contact are explicitly published; Contact's organizer supplies the server-side recipient.
- CASH/COMP issuance requires a reason, recipient and event/tier selection. CASH uses the server's current price; COMP costs zero. Both consume available inventory and queue tickets. Repeated requests with the same request ID do not issue twice. No online-payment proof is manufactured.
- Reconciliation exports approved orders, source, buyer, tier, quantities, amounts, transfer reference and approver. Order totals repeat on line rows for context; the footer totals distinct orders. Formula-like user text is neutralized in CSV. Filter large exports by event/date (maximum 10,000 orders).
- The audit view combines owner actions and the immutable scan ledger. It has no edit/delete API. Check-in views show effective admission counts and conflicts. Polling runs every 12 seconds while visible, backs off on failure and resumes when visible; push is a convenience. iPhone push needs installation on the Home Screen and live VAPID configuration.

## Staff preparation and admission

1. Owner creates an invite-only STAFF account with a temporary password. Staff must replace it before scanner APIs work. Deactivation revokes server sessions without removing historical attribution.
2. Sign in on the staff hostname, open the scanner, select the event and tap **Prepare for event** while connected. The device downloads public verification keys and admission-only ticket data into IndexedDB. No buyer email, phone, bank, pricing or payment data is stored in the manifest. The generic PWA shell can then reload offline.
3. With connectivity, check-ins go directly to the server; simultaneous scans on two phones cannot both succeed. The camera decodes QR locally. A QR image and manual token entry are available if camera permission or hardware is unavailable.
4. **During an outage, use one offline scanner for the whole event.** One offline device per gate does not prevent cross-gate duplicate entry. The scanner verifies signatures and event locally, rejects known voids/duplicates, and durably queues admissions. A valid signed ticket missing from the prepared list requires explicit staff confirmation and is flagged for owner review. A lost online response is provisional and reconciled using the same scan ID.
5. Watch last-sync age and pending-scan count. New approvals, refunds, cancellations and other phones' scans require connectivity to reach this phone. Automatically retry sync, or tap **Sync now**. Network failure never drops queued scans. Authenticate again as the same staff member when needed; an online authentication denial stops further scanning. Changing account/event cannot silently submit someone else's outbox.
6. Multiple offline phones can admit the same ticket. At sync, the earliest valid corrected scan becomes the effective check-in. The ledger remains append-only: a conflict entry identifies a displaced earlier recorded check-in instead of changing its historical result. Review `CONFLICT`, `DUPLICATE`, invalid and void outcomes. This detects cross-device offline duplicate entry after the fact; it cannot prevent it.
7. Prepared scanning expires at event end or the event-day grace boundary, whichever comes first. Ended-event holder data is cleared. Pending admission evidence remains available for sync/recovery. Do not discard it. Logout with pending scans is blocked until sync or an explicit export-and-clear decision. Exported JSON contains ticket tokens: keep it private and use it only for admission reconciliation through authenticated staff tooling. Server batch sync accepts corrected scan times from the last seven days, up to five minutes ahead; older evidence requires owner review.

Step 5 must configure durable public-banner/private-proof storage, hosted migrations and pooler, shared rate limits, server origins/cookie domain, VAPID/push, Google Places credentials/restrictions/attribution, Resend/DNS/webhooks, scheduling and deployment.
